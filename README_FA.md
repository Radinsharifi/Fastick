# FASTICK (فستیک) — سامانه هوشمند حضور و غیاب مدارس

این پروژه یک **MVP کامل و قابل اجرا** برای سناریویی است که تعریف شد: مدرسه ثبت‌نام می‌کند، برای هر زنگِ هر شیفت ساعت شروع و پایان می‌گذارد، دانش‌آموزان را با Excel وارد می‌کند، معلم‌ها را در سامانه یا با Excel تعریف می‌کند، هر معلم فقط کلاس‌های خودش را می‌بیند، غایبین را ثبت می‌کند، معاون/مدیر وضعیت ثبت کلاس‌ها را لحظه‌ای می‌بینند، برای معلم یادآوری می‌فرستند، مدیر/معاون از گزارش کلاس برای اولیای غایبین پیامک می‌فرستند و گزارش Excel/PDF قابل دریافت است.

> این نسخه برای **MVP و پایلوت واقعی** طراحی شده است. قبل از فروش گسترده به مدارس، موارد بخش «قبل از Production» را انجام بده.

---

## 1) تکنولوژی‌ها

- Frontend: React + TypeScript + Vite + Recharts
- Backend: Python + FastAPI + SQLAlchemy
- Database در سرور: PostgreSQL
- Database برای تست ساده بدون Docker: SQLite
- Reverse Proxy: Nginx
- Authentication: JWT + Password Hash
- Excel: openpyxl
- PDF فارسی: ReportLab + arabic-reshaper + python-bidi
- SMS: لایه جداگانه Provider؛ حالت پیش‌فرض `console` است.
- Deployment: Docker Compose
- UI: RTL، Responsive و قابل استفاده با موبایل
- PWA پایه: قابلیت Add to Home Screen برای تجربه شبیه اپ؛ مرورگرهای سازگار اعلان نصب بومی را نمایش می‌دهند.
- فونت Vazirmatn به‌صورت محلی همراه frontend ارائه می‌شود؛ مرورگر برای stylesheet یا فونت به Google Fonts متصل نمی‌شود.

# 3) سریع‌ترین راه برای تست روی ویندوز — بدون Docker

این روش برای زمانی است که Virtualization سیستم هنوز فعال نیست.

### پیش‌نیاز

1. Python 3.12 یا جدیدتر
2. Node.js 20/22 یا جدیدتر
3. اینترنت برای نصب پکیج‌ها در اولین اجرا

### اجرا

روی فایل زیر دوبار کلیک کن:

```text
run-local.bat
```

اسکریپت:

1. virtual environment پایتون می‌سازد.
2. وابستگی‌های backend را نصب می‌کند.
3. Backend را با SQLite روی پورت 8000 اجرا می‌کند.
4. وابستگی‌های React را نصب می‌کند.
5. Frontend را روی پورت 5173 اجرا می‌کند.
6. مرورگر را باز می‌کند.

آدرس وب‌اپ:

```text
http://localhost:5173
```

Swagger/API:

```text
http://localhost:8000/docs
```

در این حالت PostgreSQL لازم نیست و دیتابیس محلی در فایل زیر ساخته می‌شود:

```text
backend/attendance.db
```

این فقط برای تست توسعه است؛ برای سرور واقعی PostgreSQL استفاده کن.

# 6) جریان واقعی کار مدرسه

## مدیر مدرسه

1. وارد صفحه ثبت‌نام می‌شود.
2. نام مدرسه، کد مدرسه، اطلاعات خودش را ثبت می‌کند.
3. شیفت‌ها را تعریف می‌کند؛ مثال:
   - صبح: 4 زنگ، هرکدام با ساعت شروع و پایان خودش
   - عصر: 3 زنگ، هرکدام با ساعت شروع و پایان خودش
4. 7 روز Trial فعال می‌شود.
5. کلاس‌ها را تعریف می‌کند.
6. Excel دانش‌آموزان را وارد می‌کند.
7. معلم، معاون و مدیرهای دیگر را تعریف می‌کند.
8. هر معلم را به یک یا چند کلاس و درس وصل می‌کند.

## معلم


- تعداد غیبت‌ها.
- تعداد دیرآمده‌ها.

- نمودار 7 روز اخیر.

معاون می‌تواند برای معلم:

- اعلان داخل سامانه بفرستد.
- در صورت فعال‌کردن Provider، SMS بفرستد.

# 7) روش تعریف معلم‌ها — تصمیم UX

برای استفاده روزمره، روش اصلی **داخل خود وب‌اپ** است؛ چون تعداد معلم‌ها معمولاً آن‌قدر نیست که مدیر مجبور باشد هر بار Excel مدیریت کند.

اما برای راه‌اندازی سریع مدرسه، Import Excel کارکنان هم پیاده شده است.

نکته مهم: **معلم چند بار ساخته نمی‌شود.**

مثلاً فایل می‌تواند این دو سطر را داشته باشد:

```text
محمد احمدی | 0912... | T100 | معلم | 7/1 | ریاضی
محمد احمدی | 0912... | T100 | معلم | 7/2 | ریاضی
```

سیستم یک کاربر «محمد احمدی» می‌سازد و دو Assignment ثبت می‌کند:

```text
Teacher → 7/1 → ریاضی
Teacher → 7/2 → ریاضی
```

پس راه‌حل درست دیتابیسی تکرار User نیست؛ رابطه Many-to-Many از طریق `teacher_assignments` است.

# 9) نقش‌ها و سطح دسترسی

### Teacher

- فقط Assignmentهای خودش
- فقط اسامی دانش‌آموزان کلاس‌های خودش
- ثبت/ویرایش حضور و غیاب کلاس خودش
- مشاهده اعلان‌های خودش

### Deputy

- مشاهده همه کلاس‌های همان مدرسه
- مشاهده وضعیت ثبت/ثبت‌نشده
- ارسال Reminder
- مشاهده دانش‌آموزان
- گزارش Excel/PDF

### Manager

همه دسترسی‌های معاون +

- ایجاد/ویرایش کاربر
- نقش‌ها
- کلاس‌ها
- شیفت‌ها
- تعداد زنگ‌ها
- درخواست تمدید اشتراک

### Platform Admin

این اکانت متعلق به صاحب سامانه است:

- مشاهده مدارس
- تعداد دانش‌آموزان پلتفرم
- فعال‌سازی دستی اشتراک
- مشاهده آمار تجمیعی استفاده در مسیر `/owner/insights`

برای ورود Platform Admin، فیلد کد مدرسه را خالی بگذار و با شماره/رمز موجود در `.env` وارد شو.

## آمار استفاده

- بازدید صفحه‌ها پس از ورود کارکنان، بدون نمایش درخواست رضایت یا استفاده از کوکی، برای آمار کلی ثبت می‌شود.
- بازدیدها به شناسه حساب، مدرسه و نقش متصل‌اند؛ نام دانش‌آموز و جزئیات حضور و غیاب در رویدادهای بازدید ذخیره نمی‌شوند.
- رویدادهای عملیاتی مانند ورود موفق و ثبت حضور نیز در Audit Log سامانه ثبت می‌شوند؛ داشبورد مالک بخشی از این آمار تجمیعی را نشان می‌دهد.
- پنل `/owner/insights` فقط برای Platform Admin در دسترس است و از همان ورود و نقش موجود استفاده می‌کند؛ مسیر مخفی به‌تنهایی کنترل دسترسی نیست.
- توکن ورود همچنان در `localStorage` مرورگر نگهداری می‌شود.

## وابستگی‌های شبکه

- فایل‌های رابط کاربری، stylesheetها، آیکون‌ها و فونت از خود برنامه ارائه می‌شوند و برای نمایش رابط، درخواست به CDN یا سرویس font ثالث ندارند.
- پیامک واقعی فقط در صورت تنظیم `SMS_PROVIDER=kavenegar` و کلید معتبر به API کاوه‌نگار ارسال می‌شود. در حالت پیش‌فرض `console`، پیام بیرون از برنامه ارسال نمی‌شود.
- هنگام build/deploy، Docker برای دریافت imageهای پایه و نصب وابستگی‌های Python و npm به registryها نیاز دارد؛ این وابستگی‌های build با درخواست‌های مرورگر هنگام استفاده از وب‌اپ فرق دارند.

## ورود آزمایشی کارکنان

در نسخه نمایشی، رمز اولیه معلم و معاون برابر کد پرسنلی آن‌هاست؛ رمز در دیتابیس به‌صورت هش‌شده ذخیره می‌شود. رمز مدیر مدرسه جداگانه است. این سیاست برای محیط واقعی امن نیست و پیش از Production باید حذف شود.

ورود روی همان دستگاه تا ۹۰ روز باقی می‌ماند، مگر اینکه کاربر از حساب خارج شود یا توکن منقضی شود. روی دستگاه مشترک، پس از استفاده حتماً خروج از حساب را بزنید.

تاریخ‌های نمایشی و انتخاب بازه گزارش‌ها از تقویم هجری شمسی (خورشیدی) استفاده می‌کنند. ساعت نوار بالا به وقت تهران و بدون ثانیه نمایش داده می‌شود. تاریخ شمسی در رابط به تاریخ میلادی برای API تبدیل می‌شود؛ API و دیتابیس همچنان تاریخ میلادی را ذخیره می‌کنند. کد مدرسه را می‌توان جداگانه روی دستگاه ذخیره کرد؛ نام کاربری و رمز عبور را مرورگر مدیریت می‌کند.

# 10) Multi-Tenant برای 100 مدرسه

هر جدول اصلی دارای `school_id` است.

مثال:

```text
schools
users
students
classrooms
teacher_assignments
attendance_sessions
attendance_records
notifications
```

Queryهای حساس با `school_id` محدود شده‌اند.

بنابراین:

```text
مدرسه A ≠ مدرسه B
```

و اطلاعات مدارس در یک دیتابیس مرکزی هستند ولی منطقی از هم جدا می‌شوند.

برای 100 مدرسه و حتی حدود 100,000 دانش‌آموز PostgreSQL برای این مدل کاملاً مناسب است، به شرط Index و Query درست که در مدل‌های اصلی لحاظ شده است.

# 11) طراحی دیتابیس حضور و غیاب

ما Presence همه دانش‌آموزها را در هر زنگ ذخیره نمی‌کنیم؛ این حجم اضافه و غیرضروری ایجاد می‌کند.

هر زنگ یک Session دارد:

```text
attendance_sessions
school_id
classroom_id
teacher_id
date
period_number
subject
```

اگر غایب/موجه/دیرآمده وجود داشت فقط Exception ذخیره می‌شود:

```text
attendance_records
session_id
student_id
status
reason
parent_sms_sent
```

اگر کلاس غایب ندارد، Session ثبت می‌شود ولی Record ندارد.

این مدل هم سریع‌تر است و هم گزارش‌گیری راحتی دارد.

# 12) SMS اولیا

پیش‌فرض:

```env
SMS_PROVIDER=console
```

یعنی SMS واقعی ارسال نمی‌شود و متن در Log backend چاپ می‌شود. این حالت برای تست امن است.

لایه SMS در:

```text
backend/app/services/sms.py
```

جدا شده است تا Provider را بدون تغییر منطق حضور و غیاب عوض کنی.

یک Adapter اولیه برای Kavenegar هم وجود دارد. برای سرویس واقعی، API Key را در Environment Variable قرار بده؛ هرگز داخل کد یا Git قرار نده.

ارسال SMS بعد از ثبت حضور و غیاب در BackgroundTask انجام می‌شود تا معلم منتظر پاسخ پنل پیامک نماند.

برای تعداد مدارس بالاتر، این بخش را به Queue منتقل کن:

```text
FastAPI → Redis → Celery/RQ Worker → SMS Provider
```

# 13) گزارش‌ها

- گزارش به‌صورت پیش‌فرض برای امروز است؛ بازه شروع و پایان شمسی نیز قابل انتخاب است.
- فقط کلاس‌هایی که در بازه انتخابی برایشان حضور و غیاب ثبت شده نمایش داده می‌شوند؛ برای بررسی اسامی، کلاس را باز کنید.
- شمارش‌های یک روز فقط مربوط به همان روز هستند. ارسال پیامک نیز فقط برای یک روز مشخص مجاز است و برای هر کلاس جداگانه انجام می‌شود.
- Excel دانلود می‌شود.
- PDF دانلود می‌شود.

پس همین Endpoint می‌تواند برای:

- روزانه
- هفتگی
- ماهانه
- ترم
- سال تحصیلی

استفاده شود.

ساختار دیتابیس برای نمودارهای بیشتر آماده است.

دانش‌آموزان را می‌توان از صفحه دانش‌آموزان به‌صورت دستی اضافه یا ویرایش کرد؛ غیرفعال‌کردن رکورد به‌جای حذف آن، تاریخچه حضور و غیاب را حفظ می‌کند. اطلاعات کارکنان و تخصیص کلاس معلمان نیز از صفحه کاربران قابل ویرایش است.

# 16) Deploy روی VPS

روی Ubuntu:

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-plugin nginx certbot python3-certbot-nginx
sudo systemctl enable --now docker
```

سورس را روی سرور ببر، سپس:

```bash
cp .env.example .env
nano .env
```

رمزها را تغییر بده.

سپس:

```bash
docker compose up -d --build
```

Nginx Host Server را روی `127.0.0.1:8080` Reverse Proxy کن.

SSL:

```bash
sudo certbot --nginx -d attendance.example.com
```

در Production پورت PostgreSQL را Public نکن؛ خط `5432:5432` را از compose حذف کن.

```text
→ فشرده‌سازی
→ رمزگذاری
→ فضای ذخیره‌سازی جدا
→ نگهداری حداقل 14 نسخه روزانه
```

Restore را هم حداقل ماهی یک‌بار تست کن؛ Backupی که Restore نشده، قابل اعتماد نیست.

# 21) پیشنهاد مسیر توسعه

اول با **3 تا 5 مدرسه** پایلوت کن، نه 100 مدرسه.

چک‌های واقعی:

```text
□ معلم زیر 30 ثانیه حضور و غیاب را ثبت می‌کند؟
□ معاون بدون تماس و رفت‌وآمد می‌فهمد چه کلاسی ثبت نکرده؟
□ ورود Excel بدون کمک برنامه‌نویس انجام می‌شود؟
□ پیامک والدین قابل کنترل است؟
□ گزارش اداره بدون ویرایش دستی قابل استفاده است؟
□ مدیر حاضر است بابت آن پول بدهد؟
```

اگر این 6 مورد تیک خورد، بعد سراغ اتوماسیون بیشتر و Scale برو.
